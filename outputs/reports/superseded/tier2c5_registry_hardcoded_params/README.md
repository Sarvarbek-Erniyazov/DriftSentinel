# Superseded: registry artifacts carrying hardcoded model parameters

**Preserved 2026-08-04, Tier 2C.5.**

## What these files are

The `model_registry.json`, `registry_history.csv` and `model_comparison.json`
produced before `src/models/registry.py` was corrected to read `lgbm_v1`'s tree
count from the training run instead of asserting it.

## What was wrong with them

`registry.py` hardcoded:

```python
params = {"n_estimators": 173, "learning_rate": 0.05, "num_leaves": 63}
notes  = "... Early stopping at 173 trees."
```

`173` was the tree count from **before** the Tier 2A.1 target switch. After the
switch, early stopping on the 30-day target settled at a different iteration
(recorded as `best_iteration` in `outputs/models/training_summary.json`), but the
literal in `registry.py` did not move with it.

So the registry's record of the **active production model** disagreed with the
model it described — in both the `params` field and the human-readable note, and
therefore in `registry_history.csv` too.

## Why it matters beyond the wrong number

A registry exists to make an artifact's provenance checkable. A registry whose
provenance is **typed rather than read** can disagree with its own artifact,
which is the single failure it exists to prevent.

This is the same defect class as:

- `TARGET_COLS` hash randomisation (`README_MUST_INCLUDE` R-6) — output that was
  correct-looking for reasons unrelated to being correct;
- the stale hand-typed AUCs inside `defense.py`'s generated `findings` prose
  (corrected the same day).

In all three, nothing was wrong with the computation. The defect was a value
asserted next to a value that was measured, with nothing forcing them to agree.

## What replaced them

Regenerated by `python src/models/registry.py` after the fix, which now reads
`best_iteration` and the hyperparameters from
`outputs/models/training_summary.json`, and derives `train_rows` from the
evaluation report rather than from a literal.

Recorded as evidence in `docs/09_experiment_tracking_decision.md` §5: this is one
of the four traceability defects that motivated **declining MLflow**, because
`mlflow.log_param("n_estimators", 173)` would have logged the wrong number just
as faithfully.
